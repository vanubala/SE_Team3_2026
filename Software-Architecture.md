# Software Architecure

## The main quality attributes

### Security

Security is the most important quality attribute of our system. Access to resources is restricted via Role-Based Access Control (**FR_05**) and secured over HTTPS with JWT authentication on all portal endpoints (**NFR_01**). For parcel collection, pickup codes are generated as random, unique, single-use tokens that invalidate immediately upon use or expiry, with a 15-minute terminal lockout enforced after 5 consecutive failed attempts (**NFR_02**). In later releases, all critical state-changing actions are recorded in an immutable audit log for full traceability and accountability (**NFR_09**, **FR_17**), and personal recipient data is permanently removed or anonymized within 24 hours upon account deletion request in compliance with GDPR (**NFR_10**, **FR_18**).

### Reliability

Reliability is core to our system. Because the platform coordinates couriers, guest recipients, and physical locker stations concurrently, operations use atomic concurrency control so compartments cannot be double-booked and no state event is lost (**NFR_04**). Furthermore, faults are strictly isolated (**NFR_07**): if a single locker station goes offline or a compartment door jams, affected parcels transition to `LOCKER_UNAVAILABLE` (**FR_11**) while all other compartments and stations continue operating nominally. Overall, the system targets **99.5% uptime** (**NFR_06**), enhanced in future releases with local terminal caching of active pickup codes during temporary network drops (**NFR_08**).

### Usability

Usability is essential for a frictionless delivery and pickup experience. In the MVP, recipients operate as guests with zero registration overhead: they receive a single-use pickup PIN/QR code and station details via SMS/email (**FR_01**, **FR_07**) and complete collection at the terminal in two steps—entering the code and retrieving the parcel (**FR_08**). For couriers, the system automatically suggests the smallest suitable compartment based on parcel size (**FR_04**, **C6**) and allows direct deposit at the kiosk by scanning the Parcel ID (**FR_06**). To prevent queues at physical terminals, portal pages respond in under 2 seconds (**NFR_05**) and compartment doors unlock within 3 seconds of a valid code or Parcel ID scan (**NFR_03**). Where usability conflicts with security—such as enforcing a 15-minute lockout after 5 wrong PIN attempts—we prioritize security, reflecting the architectural trade-off that not all quality attributes can be maximized simultaneously.


## Software Architecture
To satisfy our stakeholders' top three quality attributes (see above) while fitting the constraints of a 6-people team, our Smart Parcel Locker System adopts a hybrid architectural style : a Layered Client-Server Architecture with Event-Driven Elements : 
- Client-Server (Overall System): multiple clients (Courier Dashboard, Recipient Portal, Admin View and Physical Locker) communicate over HTTPS/REST API with a shared backend server and database. They need real-time access to compartment availabity and parcel status, but they shoudn't have access to the database directly.
    * All sensitive data stays protected behind the API boundary
    * Prevents race conditions : e.g. two parcels assigned to the same compartment simultaneously.
- Layered Architecture (Internal Backend ) : Backend is organised into four strict top-down layer : Presentation (Role-specific UIs), Application (Controllers), Business (Service) and Data Access (Repositories)
    * Maps onto our sequence diagrams
    * Enforces Separation of Concerns + Prevents UI or routing code from bypassing domain validation or corrupting the lockers
    * Multiple UIs can use the same business logic without duplication
    * Domain rules testable without live database and switching storage across releases only affects the Repo Layer
    * Lets our team work concurrently across layers with minimal conflicts
- Event-driven elements : mostly for sending asynchronous notification (Notification Gateway) when the parcel has been deposited in its assigned compartment but can be used for hardware malfunction detection, and expiration reminders.
    * Offloading external SMS/email API calls prevents network delays from freezing the kiosk screen during physical drop-offs
    * If the external SMS/email provider is temporarily down, the parcel deposit still succeeds in the database and the notification retries independently.

## Network Communication and Authentication
Our Smart Parcel Locker System uses HTTPS, REST APIs and JSON to connect the Courier Dashboard, Recipient Portal, Admin View and physical locker terminals to the shared backend:
- **HTTPS:** clients send requests to the backend over HTTP secured by TLS. TLS encrypts the connection and uses the server’s certificate to verify its identity. This protects credentials, pickup codes and parcel information while travelling over the network, supporting **NFR_01**.
- **REST API:** the backend exposes resources through URLs and HTTP methods. For example, the Courier Dashboard calls `POST /api/parcels` , and the Admin View calls `PATCH /api/admin/compartments/{id}/status` (or `PATCH /api/admin/lockers/{id}`) to change a compartment's or locker station's operational status. In Release 1, the Recipient Portal also calls `GET /api/parcels/{id}` to retrieve live parcel status (**FR_11**). These endpoints give all clients a common interface while keeping business rules in the backend.
- **JSON and request processing:** clients exchange data using JSON request and response bodies with the `application/json` content type. A deposit request contains the parcel identifier and the locker station identifier (which maps to the assigned compartment via its `lockerId` foreign key). The backend’s API controller validates this data, calls the appropriate business service, and accesses PostgreSQL through the data access layer. It then returns a JSON response with an HTTP status code indicating the result, following our layered architecture.
- **Authentication and tokens (JWT):** web users (Couriers and Administrators in the MVP, plus Recipients in Release 1) log in through `POST /api/auth/login` over HTTPS. After validating their credentials, the backend issues a signed JSON Web Token (JWT) containing the user’s identifier and role (**NFR_01**). Clients include this token in the `Authorization: Bearer <token>` header on subsequent requests so the backend can statelessly verify the user without requesting their password again. Tokens have short expiration times and are cleared on logout.
- **Role-based authorisation:** authentication middleware verifies the JWT signature and identifies the account associated with each request. The backend then checks its roles and the requested resource before allowing the operation (**FR_05**). For example, a courier can register parcels and assign compartments, an administrator can update locker or compartment statuses, and (in Release 1) a recipient can retrieve their own parcel. These checks happen on the server for every protected operation.
- **Physical locker communication:** each terminal authenticates using its own device credential and exchanges JSON messages with the backend over HTTPS. It reports availability, door events and hardware problems, and receives authorised commands. The courier enters the pre-assigned `Parcel ID` at the assigned locker station to unlock the target compartment (**FR_06**), while guest recipients authenticate their pickup solely using their single-use PIN/QR code (**FR_02**, **NFR_02**). Door commands have unique identifiers so retries do not trigger duplicate actions, and the terminal reports execution results rather than the backend assuming that an accepted command succeeded.
- **Event-driven communication:** after a deposit is confirmed and saved, the backend produces an event for the Notification Gateway, which contacts the SMS/email provider to send the recipient's pickup code and locker details (**FR_07**). This keeps notification delivery separate from the synchronous deposit request (**NFR_03**). Dashboards can retrieve updates through REST polling; if immediate updates are needed, server-sent events can push status changes over a persistent HTTPS connection.
- **Errors and network failures:** clients interpret HTTP status codes and JSON error responses, such as 401 for invalid or expired JWTs/pickup codes, 403 for insufficient role permissions, 409 for compartment assignment conflicts, and 429 when a terminal is temporarily locked out after 5 failed PIN attempts (**NFR_02**). Timeouts, controlled retries and duplicate protection handle interrupted connections so a client losing connectivity after the backend has already processed an operation does not cause inconsistent state.

## Database
For our Smart Parcel Locker System, we propose using a relational SQL database, managed by PostgreSQL:
- **Database Management System (DBMS):** PostgreSQL stores and retrieves our data, executes SQL queries, enforces constraints, handles transactions and controls database permissions. Its support for related data and reliable concurrent updates makes it suitable for managing parcels and compartment allocations.
- **Data organisation and relationships:** our system contains related entities such as users, roles, parcels, couriers, locker sites and compartments. Each locker site (`Lockers`) is composed of multiple compartments (`Compartments`), modelled via a `lockerId` foreign key on each compartment so a parcel is assigned to a specific compartment belonging to a locker station. Primary and foreign keys represent these relationships, while constraints prevent invalid references.
- **Access from code:** the backend connects to PostgreSQL through a database driver. Following our layered architecture, business services call a data access layer (repositories) containing parameterised SQL queries or ORM operations. This separates database access from API handling and business rules. Parameterised queries help prevent SQL injection, database credentials are kept outside version control, and a connection pool allows connections to be reused efficiently.
- **Roles and access control:** users are connected to roles through a `user_roles` table (or role attribute) supporting our system roles (`Courier`, `Administrator`, and `Recipient` in Release 1) (**FR_05**). The backend checks these roles and parcel ownership or courier assignment before granting access. Clients communicate through the API rather than accessing the database directly. PostgreSQL permissions also restrict what the backend’s database account can do.
- **Transactions and concurrency:** multiple couriers may try to reserve a compartment simultaneously. Transactions, constraints and appropriate row-level locking ensure that only one active allocation succeeds for a given compartment (**NFR_08**). Reserving a compartment and assigning the parcel must succeed or fail together so that the database remains consistent.
- **History and reporting:** the database stores current parcel statuses and separate event records (`ParcelEvents`) for tracking and investigation (**FR_03**, **FR_17**). SQL supports queries across these records, such as finding expired pickups (**FR_14**), checking station occupancy (**FR_09**), and inspecting historical parcel or maintenance logs (**FR_17**).
- **Performance and maintenance:** indexes support frequent searches, such as finding a parcel by tracking number (`trackingNumber`) or listing available compartments at a locker site (`lockerId`), helping meet **NFR_04**. Schema changes are managed through version-controlled migrations, while regular backups and tested restoration procedures support recovery from data loss.
