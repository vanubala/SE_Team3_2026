## The main quality attributes

### Security

Security is the most important part of our system. The system logs actions, for traceability and accountability. Furthermore, we ensure that the right entity receives access to the appropriate resources through role-based access control (FR_05), secure login on every endpoint (NFR_01), and pickup codes that are random, unique and single-use, with a 15-minute lockout after 5 wrong attempts (NFR_06). Personal and customs data is encrypted and deleted on request (NFR_02, NFR_03).

### Reliability

Reliability is core to our system. Since the parcel management system facilitates serves many parties and entities it is important that one the parcel management system doesn't allow one or several errors to impact our core service. If for example, one locker goes offline or one door jams, that locker's parcels move to a "Locker Unavailable" status (FR_04) and all other lockers and compartments should keep operating nominally. Operations should use proper concurrency control, so no event is lost or mismanaged. Our target is 99.5% uptime.

### Usability

Usability is key to a smooth experience for all parties. Recipients do not need to log in to track their parcel: they can use the secure code provided by our system, or receive SMS updates on the number the courier registered for them or that they signed up with. Pickup is then two steps to maintain simplicity: enter the code or tap "open" in the app (FR_07), then take the parcel. Opening through the app is only allowed if the phone number has been verified against the one the courier provided. A courier gets a compartment suggested by parcel size (C6) and only needs to confirm it. To avoid long waits, pages respond in under 2 seconds (NFR_04) and a compartment opens within 3 seconds of a valid code (NFR_05). Where usability conflicts with security, such as the lockout after wrong codes, we choose security, which goes back to the principle that we cannot maximise all attributes.


## Software Architecture
For our Smart Parcel Locker System we are going for a hybrid architectural approach by going for a Layered Client-Server Architecture with Event-Driven Elements : 
- Client-Server (Overall System): multiple clients (Courier Dashboard, Recipient Portal, Admin View and Physical Locker) communicate over HTTPS/REST API with a shared backend server and database. They need real-time access to compartment availabity and parcel status, but they shoudn't have access to the database directly.
- Layered Architecture (Internal Backend ) : Based on our sequence diagrams --> easier to understand and to divide between the members. Helps with security and information hiding.
- Event-driven elements : mostly for sending asynchronous notification (Notification Gateway) when the parcel has been deposited in its assigned compartment but can be used for hardware malfunction detection, and expiration reminders.

## Network Communication and Authentication
Our Smart Parcel Locker System uses HTTPS, REST APIs and JSON to connect the Courier Dashboard, Recipient Portal, Admin View and physical locker terminals to the shared backend:
- HTTPS: clients send requests to the backend over HTTP secured by TLS. TLS encrypts the connection and uses the server’s certificate to verify its identity. This protects credentials, pickup codes and parcel information while travelling over the network, supporting NFR_01.
- REST API: the backend exposes resources through URLs and HTTP methods. For example, the Recipient Portal calls GET /parcels/{id} to retrieve a parcel’s status, the Courier Dashboard calls POST /parcels/{id}/deposit to confirm a deposit, and the Admin View calls PATCH /admin/lockers/{id} to change a locker’s operational status. These endpoints give all clients a common interface while keeping business rules in the backend.
- JSON and request processing: clients exchange data using JSON request and response bodies with the application/json content type. A deposit request can contain the parcel and compartment identifiers. The backend’s API controller validates this data, calls the appropriate business service, and accesses PostgreSQL through the data access layer. It then returns a JSON response with an HTTP status code indicating the result. This follows our layered architecture.
- Authentication and sessions: web users log in through POST /auth/login over HTTPS. After validating their credentials, the backend creates a session and returns its identifier in a Secure, HttpOnly cookie. The browser sends this cookie with subsequent requests so the backend can identify the user without requesting their password again. Sessions expire and are invalidated on logout; cookie-based requests also receive protection against cross-site request forgery.
- Role-based authorisation: authentication middleware identifies the account associated with each request. The backend then checks its roles and the requested resource before allowing the operation (FR_05). For example, a recipient can retrieve their own parcel, a courier can confirm an authorised deposit, and an administrator can update locker status. These checks happen on the server for every protected operation.
- Physical locker communication: each terminal authenticates using its own device credential and exchanges JSON messages with the backend over HTTPS. It reports availability, door events and hardware problems, and receives authorised commands. Courier QR/PIN authentication is checked separately from the terminal’s identity (FR_13). Door commands have unique identifiers so retries do not trigger duplicate actions, and the terminal reports execution results rather than the backend assuming that an accepted command succeeded.
- Event-driven communication: after a deposit is confirmed and saved, the backend produces an event for the Notification Gateway, which contacts the SMS/email provider (FR_23). This keeps notification delivery separate from the deposit request. Dashboards can retrieve updates through REST polling; if immediate updates are needed, server-sent events can push status changes over a persistent HTTPS connection.
- Errors and network failures: clients interpret HTTP status codes and JSON error responses, such as 401 for invalid authentication and 403 for insufficient permission. Timeouts, controlled retries and duplicate protection handle interrupted connections. This is necessary because a client may lose its connection after the backend has already processed an operation.


## Database
For our Smart Parcel Locker System, we propose using a relational SQL database, managed by PostgreSQL:
- Database Management System (DBMS): PostgreSQL stores and retrieves our data, executes SQL queries, enforces constraints, handles transactions and controls database permissions. Its support for related data and reliable concurrent updates makes it suitable for managing parcels and compartment allocations.
- Data organisation and relationships: our system contains related entities such as users, roles, parcels, couriers, locker sites and compartments. For example, a locker site contains multiple compartments, and a parcel is linked to its sender, recipient and assigned compartment when applicable. Primary and foreign keys represent these relationships, while constraints prevent invalid references.
- Access from code: the backend connects to PostgreSQL through a database driver. Following our layered architecture, business services call a data access layer containing parameterised SQL queries or ORM operations. This separates database access from API handling and business rules. Parameterised queries help prevent SQL injection, database credentials are kept outside version control, and a connection pool allows connections to be reused efficiently.
- Roles and access control: users are connected to roles through a user_roles table, allowing one account to have multiple roles, such as sender and recipient (FR_05). The backend checks these roles and parcel ownership or courier assignment before granting access. Clients communicate through the API rather than accessing the database directly. PostgreSQL permissions also restrict what the backend’s database account can do.
- Transactions and concurrency: multiple couriers may try to reserve a compartment simultaneously. Transactions, constraints and appropriate locking ensure that only one active allocation succeeds for a given compartment. Reserving a compartment and assigning the parcel must succeed or fail together so that the database remains consistent.
- History and reporting: the database stores current parcel statuses and separate event records for tracking and investigation (FR_03, FR_04, FR_06). SQL supports queries across these records, such as finding expired pickups, checking occupancy and preparing authorised customs exports. Each customs export is logged with the administrator, timestamp and request reference (FR_18).
- Performance and maintenance: indexes support frequent searches, such as finding a parcel by tracking number or listing available compartments, helping meet NFR_04. Schema changes are managed through version-controlled migrations, while regular backups and tested restoration procedures support recovery from data loss.
